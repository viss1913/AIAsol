# Механика ИИ: двухфазный запрос (классификация → контекст → ответ)

Краткое описание того, как бэкенд обрабатывает сообщение пользователя: **два последовательных вызова LLM** через OpenRouter, между ними — **подбор динамического системного промпта из БД** по «команде».

## Зачем так

1. **Фаза A** — модель выбирает **маршрут** (строка-команда вида `/start`, `/goLife`, …), не генерируя длинный ответ пользователю.
2. **Между фазами** — по выбранной команде из таблицы `ai_commands` и настроек бота собирается **релевантный системный промпт** (база + сценарий + при необходимости персональные данные).
3. **Фаза B** — та же модель (в коде — один и тот же `AI_MODEL`) отвечает пользователю уже с этим промптом и **историей диалога**.

## Где в коде

| Часть | Файл |
|--------|------|
| Вызов 1: классификация → команда | `ai.js` → `classifyIntent` |
| Вызов 2: ответ пользователю | `ai.js` → `askAI` |
| Промпт классификатора из БД | `context.js` → `getClassifierContext` |
| Сбор системного промпта ответа | `context.js` → `getResponseContext` |
| HTTP API (полный цикл) | `api.js` → `POST /chat` |
| Telegram-бот (полный цикл + user context) | `telegram.js` |

## Данные в БД (логика)

- **`bots.base_brain_context`** — общий «мозг» бота, всегда в начале итогового системного промпта ответа.
- **`ai_commands`** (на бота завязано через `bot_id`):
  - **`command`** — идентификатор маршрута (например `/start`).
  - **`classifier`** — текст инструкций для **фазы A** (как выбирать следующую команду из сообщения пользователя).
  - **`response`** — текст инструкций/роли для **фазы B** (как отвечать в этом сценарии).
- **`sessions.last_command`** — последняя выбранная команда; от неё зависит, **какой `classifier` подтянуть** перед следующим сообщением.
- **`sessions.history`** — JSON-массив `{ role, content }` для OpenRouter.
- **`users.user_context`** (опционально) — персональный контекст; подмешивается в `getResponseContext`, если передан `userId` (в Telegram так и сделано).

## Алгоритм по шагам

1. Загрузить сессию: `last_command` (по умолчанию `'/start'`), `history`.
2. **`getClassifierContext(botId, last_command)`**  
   Взять поле `classifier` для текущей команды сессии. Если записи нет — фолбэк на команду `'/start'`.
3. **`classifyIntent(userMessage, classifierContext)`** (1-й вызов LLM)  
   В пользовательский промпт подставляются инструкции из шага 2; в системном сообщении модель объявлена классификатором.  
   **Ожидаемый вывод:** одна строка — новая команда `newCommand` (без пояснений).  
   При ошибке API в коде возвращается `'/start'`.
4. **`getResponseContext(botId, newCommand, userId?)`** (без LLM)  
   Собрать строку:
   - `base_brain_context`
   - разделитель `---`
   - `response` для `newCommand` (если нет — снова фолбэк `'/start'`)
   - при наличии `userId` и данных — блок «Контекст пользователя».
5. **`askAI(userMessage, responseContext, history)`** (2-й вызов LLM)  
   Сообщения: `[system: responseContext, ...history, user: userMessage]`.
6. Сохранить в БД: новые реплики в историю, **`last_command = newCommand`**, при необходимости лог сообщений.

## Отличие API и Telegram

- **`api.js`**: `getResponseContext(botId, newCommand)` — **без** третьего аргумента, персональный `user_context` из `users` не подмешивается.
- **`telegram.js`**: `getResponseContext(botId, newCommand, chatId)` — `chatId` используется как `userId` для выборки `user_context`.

## Важный нюанс для документации

Классификатор (**фаза A**) опирается на **`last_command`** (состояние до ответа), а системный промпт ответа (**фаза B**) — на **`newCommand`** (состояние после классификации). То есть «контекст классификации» и «контекст ответа» привязаны к **разным** ключам команды в одном цикле обработки сообщения.

## Модель и транспорт

- Провайдер: OpenRouter (`https://openrouter.ai/api/v1/chat/completions`).
- Модель задаётся в `ai.js` константой `AI_MODEL` (на момент написания документа — см. файл).
